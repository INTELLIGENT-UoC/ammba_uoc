# Decision log

Architectural and implementation decisions, with their rationale. Superseded
decisions are kept and marked, so the reasoning behind the current design stays
traceable.

|   # | Decision                                                                                                                      | Rationale                                                                                                                                              | Date       |
| --: | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------- |
|   1 | Hardhat 2 rather than Hardhat 3 for the contract                                                                              | Hardhat 3 required Node 22 and is ESM-only, which conflicted with the CommonJS toolbox of the project                                                  | 2026-02-24 |
|   2 | uv for all Python components                                                                                                  | Fast, integrated environment management and reproducible lock files                                                                                    | 2026-02-24 |
|   3 | The on-chain audit anchor is optional                                                                                         | Clearing must run without blockchain access for local development and for communities that do not need an anchor                                       | 2026-02-24 |
|   4 | The pricing function is duplicated in the settlement component                                                                | Counterfactual prices for penalties need the identical function; duplication keeps components independently deployable. The copies must stay identical | 2026-02-24 |
|   5 | CommonJS for the contract project                                                                                             | Hardhat 2 and its toolbox use `require()`                                                                                                              | 2026-02-24 |
|   6 | ~~Hash-based trade identifiers~~ superseded by #8                                                                             | The ontology requires UUID trade identifiers                                                                                                           | 2026-02-24 |
|   7 | The INTELLIGENT ontology is the wire contract                                                                                 | Interchangeability with the other GSY DEX mechanisms; translation is isolated in `adapters.py`                                                         | 2026-06-24 |
|   8 | Deterministic version 5 UUIDs for trades and pool orders                                                                      | Re-running a clearing reproduces identical objects                                                                                                     | 2026-06-24 |
|   9 | The pool is an actor on the wire, with standing orders per market slot                                                        | The trade object is bilateral, so pool-mediated exchanges need a counterparty and orders on both sides                                                 | 2026-06-24 |
|  10 | Dependency-free schema validator                                                                                              | Validation at the boundary without adding a schema library to the lock files                                                                           | 2026-06-24 |
|  11 | Schema-validating simulator of the off-chain store                                                                            | End-to-end tests of wire compatibility without an external environment                                                                                 | 2026-06-24 |
|  12 | Calibration as an offline job with a grid search                                                                              | Community-run, no heavy numerical dependencies, robust on the non-smooth objective, reproducible                                                       | 2026-06-24 |
|  13 | EWDS publish/poll transport behind the same client interface as REST                                                          | The confirmed integration path of the platform; the clearing pipeline stays transport-agnostic                                                         | 2026-08-17 |
|  14 | Lenient validation mode for inbound orders                                                                                    | Integration against environments whose order data is still being aligned with the ontology                                                             | 2026-08-17 |
|  15 | Self-trigger scheduler that discovers closed AMM markets                                                                      | The platform emits no market-close event; the idempotency check remains the safeguard                                                                  | 2026-08-18 |
|  16 | Seller-side differential pricing, with the adjusted price written into the trade price                                        | Buyers keep the uniform price; no ontology extension needed; provenance travels in the clearing summary                                                | 2026-08-24 |
|  17 | Bounded retries with back-off for network errors and HTTP 5xx                                                                 | Transient failures of the store or gateway must not fail a clearing                                                                                    | 2026-08-24 |
|  18 | Matches are settled through the GSY DEX settlement layer by a dedicated AMM settlement engine                                 | The platform settles matches on-chain; the clearing engine stays unchanged                                                                             | 2026-08-24 |
|  19 | The pool's on-chain orders are standing orders registered by the settlement engine, one per pool trade and priced at the band | Agreed pool representation; a settled order cannot be reused, and band prices never violate the settlement price check                                 | 2026-08-24 |
|  20 | UUID bytes for order, trade and market identifiers on-chain; hashed and registered mapping for actors                         | Conventions of the GSY DEX                                                                                                                             | 2026-09-04 |
|  21 | Adaptive response polling, scheduler back-off and one fixed diagnostic client identifier                                      | Keep the load on a shared gateway low, especially while an upstream service is unavailable                                                             | 2026-09-23 |
|  22 | Documentation as an MkDocs site under `docs/`, structured like the T5.4 deliverable                                           | One maintained source of documentation, reviewable with the code and built strictly in continuous integration                                          | 2026-10-13 |
